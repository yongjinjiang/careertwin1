# CareerTwin1 实施计划

日期：2026-10-19  
状态：计划稿；当前交付计划，尚未开始新版实现。

长期目标是根据目标职位生成真实、相关、便于修改的简历。当前优先完成 Profile 的建立和维护，使它成为可以独立使用的个人经历库。Profile 达到验收条件后即可交付和暂停，后续功能不构成本阶段的完成条件。

## 产品范围和实施原则

1. 以项目记录为核心。一条记录可以是具体项目，也可以是一段工作或研究阶段的概括，由用户决定详细程度。
2. 手动录入、保存、修改和覆盖均保存用户原文，不调用 LLM。用户可以在其他工具中自行整理文字后粘贴。
3. 普通项目不超过约定的 500 字，不设强制最低字数。用提示引导用户描述工作内容、个人贡献和结果，不要求用户分别维护技能、论文或成果条目。
4. 基本信息集中在独立的 Basic Info 页面或 tab，使用自由文本输入。教育、证书、奖项、联系方式、链接、所在地、工作偏好、公民身份等均可放在这里。
5. Basic Info 使用相同的记录存储形式，单位固定为 `basic info`，并以独立类型区分；不靠单位名称判断记录类型。基本信息不受普通项目的 500 字上限约束。
6. 所有项目使用同一个编辑界面。Profile 浏览页可以查看全文，通过 Edit 进入统一编辑器；基本信息允许在自己的 tab 中直接修改。
7. 不建立事实拆分、提案审核、verify、证据合并等维护流程。
8. 按里程碑验收。每个里程碑必须产生一个可实际使用、能够清楚描述完成边界的结果。

## 工程安排

新版项目命名为 **CareerTwin1**。执行 M0 时创建其独立代码库和数据存储，保留现有 CareerTwin 作为旧版参考；具体项目目录在 M0 中确定。当前这一轮仅编写和修订计划，尚不执行项目创建。旧数据迁移不属于 M0 至 M2 的范围，是否迁移以后单独决定。

新版可以沿用熟悉的 React 和 TypeScript 前端栈。旧版的文档解析、LLM 接口、导出等能力在对应里程碑到来时逐项评估复用；不整套搬入旧 Profile、审核和兼容结构。

当前仓库已有大量未提交改动。实现准备阶段应记录既有状态并隔离新版工作，不覆盖、整理或批量提交既有改动。本轮只在旧仓库的 `docs` 目录新增此计划，不修改旧版应用或历史设计文档。

第一阶段采用单用户、本地优先的建议方案：使用独立 IndexedDB 数据库保存资料，不依赖登录或后端即可完成手动录入和维护。该方案不提供跨设备同步，用户通过备份导出和恢复转移数据；云端同步若成为需求，另设里程碑。

## Profile 页面和操作约定

### 主页和统一项目编辑器

主页中央是项目原文输入区。项目名称可手动填写；留空时由原文首行生成简短显示名称，不调用 LLM。

输入区提供两个明确的操作：

- **Save as new**：保存为新的项目记录。原文持久化成功后，提供可跳过的单位和起止年份补充界面；单位留空归为个人项目，时间允许留空或选择至今。补充失败、取消或跳过不丢失已经保存的原文，也不再次新建记录。
- **Overwrite existing**：选择已有项目，展示名称、单位和时间以辨认目标，按钮明确显示将覆盖的项目。覆盖更新同一条记录的原文并保留 ID；单位和时间默认保留，只有用户明确修改时才更新。

从 Profile 点击 Edit 时，将原文和元数据载入这个编辑器，界面明确显示正在编辑哪个项目，主操作为保存修改。用户需要另建项目时，明确切换到新建模式。

保存中、保存成功和保存失败有清楚反馈；只有持久化成功才显示保存成功。失败时保留输入，连续点击保存不产生重复记录。应用内离开未保存的编辑内容时给出提示。

### 我的 Profile

- **项目 tab**：展示项目名称、单位、时间和原文前一两行。允许展开查看完整原文，提供 Edit 和删除入口。列表摘录直接来自原文，不生成另一份 AI 摘要。
- **Basic Info tab**：查看和直接编辑基本信息自由文本，明确保存。它不作为普通项目显示在项目列表中。
- 删除前明确展示目标，并让用户确认；初版不建立复杂的审核或版本历史系统。

### 导航

M1 和 M2 只提供已经可以使用的主页及 Profile 等必要入口。可选 M3 完成后，在导航增加次要的“导入简历”入口，进入独立页面；主页中央继续用于项目输入和更新。

## 最小数据约定

项目记录至少包含稳定 ID、记录类型、显示名称、用户原文、可选单位和年份、是否至今、创建时间和更新时间。Basic Info 为单独一条 `basic_info` 记录，普通项目为 `project`；基本信息不填写工作起止年份。

用户输入的原文是资料来源。显示名称、列表摘录和后续分析结果不替代原文。覆盖修改保留记录 ID 和创建时间，更新原文及修改时间；生成简历的文字以后也不自动写回 Profile。

本地存储和备份带有明确的格式版本。此时只实现新版自身的存储及备份格式，旧 CareerTwin 资料迁移另行决定。

开始实现前需要锁定 **500 字的计数方式**：建议中文按字、英文按词；混合输入需要定义一致的计数函数。编辑器显示计数，超限时保留输入并提示修改，不静默截断。这个口径可以在 M0 中落定，不影响当前计划。

时间按已讨论的年份记录，允许留空或至今；不增加月份和任职结构。

## 里程碑和验收

### M0 实现准备

范围：记录旧版工作区状态，建立独立新版工程及数据库边界，锁定文字计数规则，确定最小数据结构和页面路径。

交付：可启动的空应用、基础页面导航、数据约定和 M1 验收清单。保持原有 CareerTwin 可以独立存在，不进行旧数据迁移或公开部署。

验收：新版读写不会触及旧数据库；项目和 Basic Info 的存储及编辑入口清楚。无需预先设计下游职位分析或简历生成的内部协议。

### M1 手动建立和维护 Profile

范围：主页项目编辑器、Save as new、可跳过的单位和年份补充、Overwrite existing、Profile 项目列表、查看全文、统一编辑入口、删除，以及 Basic Info 查看和修改。

交付：从空白开始建立并维护完整 Profile 的可用版本。手动操作全程不调用 LLM。

验收场景：

- 新建一个个人项目、一条单位项目，以及一条概括整个工作或研究阶段的记录；保存后刷新和重新打开均可读取。
- Save 后跳过元数据仍保留原文；补充单位、年份或至今时正确更新同一条记录。
- Overwrite 指定目标后，项目数量不变、ID 不变，其他项目不变，原单位和时间默认保留。
- 从 Profile 的 Edit 返回统一编辑器，保存后列表、全文和原文一致；切换新建或编辑模式不会误覆盖目标。
- Basic Info 独立保存和展示，修改后不产生重复记录，也不进入普通项目列表。
- 空内容和超限内容得到清楚提示；保存失败保留输入且不显示成功；重复点击不产生重复项目。
- 普通项目录入和维护不触发任何模型请求。

M1 结束后先用真实经历完成一份 Profile，发现和修复实际录入问题，再进入 M2。

### M2 可靠的日常使用和备份

范围：完善保存状态、应用内未保存内容提示和必要的错误处理；增加包含项目、基本信息及元数据的版本化备份导出和恢复。整理桌面及手机宽度下的日常操作。

备份恢复先检查文件和格式版本，明确展示它会替换当前新版 Profile，用户确认后一次性写入。无效文件或写入失败不破坏现有资料；初版不提供复杂的合并恢复。

交付：可以长期维护、能够自行备份并恢复的 Profile 版本。

验收场景：

- 更新一个已有项目的新进展，再修改基本信息，刷新和重新打开后均保持一致。
- 导出一份备份，在独立测试环境恢复，逐条核对原文、项目数量、ID、单位和时间。
- 无效、损坏或不支持版本的备份不会覆盖当前资料；成功与失败反馈准确。
- 模拟持久化失败时保留编辑内容；应用内离开未保存编辑时能提示。
- 桌面和手机宽度下能完成新增、编辑、覆盖、浏览和备份操作，不依赖悬浮操作才能访问关键按钮。
- 使用者完成一次完整资料整理和一次后续更新，能够独立理解各入口，不需要开发者解释操作。

**M2 是本计划优先完成的交付点。达到验收条件后，可以发布或停止继续开发；发布作为单独执行步骤。M3 及所有下游功能都不影响 M2 的完成。**

### M3 可选的简历导入

启动条件：M1 和 M2 已通过，实际使用表明确实需要减少已有简历用户的首次录入工作量。

范围：独立导入页面和导航入口；首批建议支持旧项目已有解析基础的 DOCX，其他文件格式以后按需求增加。LLM 从用户上传的简历整理 Basic Info 和项目记录。

导入规则：

- 仅根据简历明示内容填写资料；缺失信息留空，不推测身份、偏好或经历。
- 有具体项目时按项目整理；只有工作或研究阶段概述时保留阶段记录，不强制拆成技能、论文和审核事实。
- 项目长度遵循与手动录入相同的规则；整理过程不得添加原文不支持的事实。
- 导入页展示基本信息草稿及项目草稿列表，用户保存后进入同一套 Profile 维护流程；项目修改仍使用统一编辑器。
- 已有项目默认新增导入，不自动匹配或覆盖旧项目。已有 Basic Info 默认保留；用户可显式选择用导入草稿替换。提供整体导入前的预览，不增加逐事实 verify 流程。
- 导入失败保留现有 Profile，不发生部分写入或静默丢失。LLM 调用只属于这个明确触发的入口。

交付：已有简历用户可以快速建立 Profile 的可选入口。

验收：用少量有代表性的简历检查项目分组、事实保留、缺失信息处理和长度；验证已有资料不会被自动覆盖。M3 的语义质量需要单独评估，不能只靠格式校验认定成功。

## 测试和工作节奏

测试围绕实际数据风险和验收场景：新建与覆盖的区别、元数据保留、Basic Info 唯一性、持久化失败、刷新读取和备份恢复。对这些行为写必要的单元、存储和界面测试，再完成一次真实浏览器操作验收；不以测试数量作为完成指标。

每个里程碑按“实现必要功能 → 跑相关测试 → 实际使用 → 修复阻碍使用的问题 → 明确验收结果”的顺序推进。只在验收完成后决定是否进入下一阶段。记录未解决的问题和可选改进，避免在开发中不断扩大当前里程碑。

M0 至 M2 无需真实模型调用。M3 若实施，再确定模型调用方式、数据处理范围、代表性案例及试跑成本，不在本轮运行模型实验。

## 后续产品方向

这些方向只用于说明长期目标，不要求提前实现接口、页面占位或兼容层。

| 方向 | 已确定的目标 | 何时详细设计 |

| Job Analysis | 分析 JD，与 Profile 比对，产生稳定、尽可能客观的 match score、总体评价及可逐项列出的依据；区分信息不足和明确不满足 | Profile 独立交付后，决定启动时再制定评分标准、评估集、重复运行和跨模型验收 |

Job Analysis 的模型、推理强度和分差阈值尚未经过实验验证；不把前期讨论的数值当成已经达到的性能。Resume Generation 的长期目标也不改变 Profile 可以独立完成并停止的边界。
